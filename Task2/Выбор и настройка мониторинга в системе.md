# Выбор и настройка мониторинга в системе

## Мотивация

Яндекс Метрика показывает поведение посетителей магазина. Для работы с заказами нужны дополнительные данные: обращения к MES API, состояние очередей, ошибки и время расчёта.

Мониторинг поможет раньше замечать задержки, находить перегруженные компоненты и проверять результат исправлений. Бизнес сможет сравнивать количество принятых, текущих и завершённых заказов.

## Выбор подхода к мониторингу

Для Shop API, CRM API и MES API выбираю **RED**:

- количество запросов;
- ошибки;
- время выполнения.

Расчёт цены и получение списка MES измеряем отдельно.

Для серверов API и обеих БД использую **USE**:

- загрузка ресурсов;
- ожидание свободного ресурса;
- ошибки.

Наблюдаем процессор, память, диск и соединения с БД. Shop DB общая для магазина и CRM, поэтому измеряем её как один ресурс.

Для RabbitMQ собираем размер и возраст очередей, скорость обработки, повторы и неподтверждённые сообщения.

## Метрики

Названия прикладных метрик ниже предложены для проекта. Точные названия метрик готовых экспортёров проверяем при подключении.

Основные обозначения:

- `counter` — счётчик событий;
- `gauge` — текущее значение;
- `histogram` — распределение значений, например длительности;
- RPS — запросы в секунду;
- p50 и p95 — время, в которое укладываются примерно 50% и 95% запросов.

Ярлыки позволяют разделять метрики по сервису, окружению и другим признакам.

| Что измеряем | Зачем | Ярлыки |
| --- | --- | --- |
| API: `http_requests_total`, RPS и доля ответов 5xx | Видеть поток запросов и ошибки. RPS рассчитываем по изменению счётчика, долю ошибок — от всех запросов того же API. | `service`, `environment`, `route`, `method`, `status_code`; для MES — `channel=b2b/operator` |
| API: `http_request_duration_seconds`, histogram | Сравнивать p50 и p95. Разделять успешные и ошибочные ответы, список MES и расчёт цены. | `service`, `environment`, `route`, `method`, `outcome` |
| MES: `price_calculation_duration_seconds`, `price_calculations_active`, `price_calculations_total` | Измерять время, количество одновременных расчётов и их результат. Проверить влияние расчётов на операторов. | `environment`, `channel`; для счётчика — `outcome=success/error` |
| RabbitMQ: ready и unacked, gauge | Ready — сообщения ждут выдачи. Unacked — выданы получателю, но обработка ещё не подтверждена. | `environment`, `vhost`, `queue` |
| RabbitMQ: публикации, успешные обработки и повторные доставки, counter | Сравнивать поступление и обработку сообщений, замечать повторяющиеся ошибки. | `environment`, `queue`, ограниченный набор `result` |
| Очередь неуспешных сообщений: количество сообщений, gauge | Замечать сообщения, требующие разбора. Считаем сообщения в очереди, связанной с DLX. Сам DLX сообщения не хранит. | `environment`, `queue` |
| Возраст самого старого ожидающего сообщения, gauge | Находить давно зависшие сообщения даже в небольшой очереди. Время публикации передаём в метаданных. Мониторинг не должен забирать сообщения из очереди. | `environment`, `queue` |
| Серверы API и RabbitMQ: CPU, память, ожидание процессора и диска, ошибки ввода-вывода | Находить нехватку ресурсов. | `environment`, `instance`, `service`, при необходимости `device` |
| БД: соединения, их предел, ожидание пула, долгие запросы и блокировки | Проверять нехватку соединений и медленные запросы. Ожидание пула измеряет API, состояние БД — экспортёр или облачный мониторинг. | `environment`, `database`; для пула — `service`, `pool` |
| БД: CPU, память, задержка диска, свободное и занятое место | Замечать нехватку ресурсов и места. | `environment`, `database`, `instance` |
| S3: объём данных, ошибки и время записи/чтения моделей | Проверять доступность файлов и планировать место. | `environment`, `bucket`, `operation`, `outcome` |
| Заказы: `orders_accepted_total`, `orders_status_current`, `orders_oldest_in_status_seconds` | Видеть входящий поток, текущие статусы и самые долгие ожидания. Состояние получаем из сохранённых данных. | `environment`, `channel`; для состояния — `status` из десяти статусов задания |
| Redis: попадания, промахи, ошибки, память и вытеснения | Проверять пользу кеша и замечать его недоступность. | `environment`, `instance`; для обращений — `operation`, `outcome` |
| `up`, ошибки сбора и время последнего успешного обновления бизнес-метрик | Замечать сбои самого мониторинга. | `job`, `instance`, `environment` |

Длительность расчёта измеряем через histogram, число текущих расчётов — через gauge, общее число и результат — через counter.

В `route` сохраняем шаблон, например `/orders/{id}`. Полный URL, SQL, имена файлов и идентификаторы отдельных заказов в ярлыки не добавляем. Они создают слишком много отдельных рядов данных.

Конкретный заказ ищем по логам и трейсам. На первом этапе метрики по каждому пользователю и числу сессий не собираем. Для проверки обращений партнёра используем логи с ограниченным доступом. Передачу моделей измеряем на уровне операций S3.

## План действий

1. DevOps размещает Prometheus, Grafana и Alertmanager во внутренней сети. Prometheus получает постоянный диск. Начальный срок хранения — 30 дней. Размер диска уточняем после первой недели. Интерфейсы доступны сотрудникам по ролям, адреса сбора метрик — только сборщику.
2. Java-разработчики подключают Micrometer к Shop API и CRM API. C#-разработчик добавляет метрики MES. Используем общий набор названий операций и статусов. Интервал сбора — 15 секунд.
3. DevOps подключает метрики RabbitMQ, серверов, PostgreSQL и S3. Бизнес-метрики обновляет отдельная задача. Её запросы и частоту ограничиваем, чтобы мониторинг не перегружал БД.
4. Создаём панели «Заказы и статусы», «API и расчёт MES», «БД, RabbitMQ и S3». Отмечаем на них релизы. Настраиваем уведомления о недоступности, устойчивых ошибках, росте очередей и остановке обработки заказов. Пороги и получателей согласуем после первых измерений.
5. На release QA проверяет заказ через магазин и API, ошибку расчёта и остановку получателя сообщений. Проверяем графики и уведомления. После внедрения сравниваем одинаковые операции, время открытия списка и число просроченных заказов.
