# Планирование: анализ проблем и поиск решений

## Проблемы системы

| Проблема | Что известно и что проверить |
| --- | --- |
| Заказы задерживаются | Клиенты ждут несколько месяцев вместо обещанных трёх недель. Производство справляется с нагрузкой. Нужно проверить передачу заказов между системами и смену статусов. Причина задержек пока неизвестна. |
| MES долго рассчитывает цену | Расчёт занимает 2–3 минуты, для сложной модели — до 30 минут. После открытия API расчётов стало больше. Нужно проверить, мешают ли они работе операторов. |
| Список заказов медленно открывается | Фильтр и пагинация не помогли. Нужно измерить время ответа API, запрос к MES DB и ожидание соединения с БД. |
| Не видно весь путь заказа | Яндекс Метрика показывает работу сайта. Внутренняя обработка и обращения партнёров к MES API остаются без общего наблюдения. |
| Возможны задержки при обмене через RabbitMQ | Нужно проверить подтверждения, повторы, обработку дублей и ошибочных сообщений. Из условия неизвестно, как эти механизмы настроены сейчас. |
| Есть точки отказа | Приложения и БД работают в одном экземпляре. Нужно проверить резервирование, резервные копии и восстановление. Наличие управляемого сервиса ещё не подтверждает наличие резервного узла. |
| Магазин и CRM используют общую БД | Нагрузка магазина может влиять на CRM и наоборот. Изменения общей структуры данных нужно согласовывать. У MES отдельная БД. |
| Исправления долго выпускаются | Сквозные проверки выполняются вручную. Критичные ошибки задерживают релизы. В команде один QA и один C#-разработчик. |

## Инициативы по приоритету

| Приоритет | Что сделать | Зачем |
| --- | --- | --- |
| 1 | Подключить метрики, логи и трейсинг пути заказа | Найти этапы, на которых возникают задержки и ошибки. Начать с MES API, CRM API и RabbitMQ. |
| 2 | Проверить надёжность обработки заказов | Проверить сохранение заказа, отправку и обработку сообщений, повторы и защиту от дублей. Ошибочные сообщения направлять в отдельную очередь для разбора. |
| 3 | Отделить долгие расчёты от работы операторов | Выполнять расчёты в фоне, ограничить их количество и поток новых заданий. Проверить запрос списка и добавить кеширование по Task5. |
| 4 | Уменьшить влияние отказов | Добавить резервные экземпляры нужных API после проверки их совместной работы. Проверить резервирование RabbitMQ и БД, копирование и восстановление данных. |
| 5 | Ускорить проверку и выпуск изменений | Автоматизировать основные сценарии заказа через магазин и API. Добавить проверки повторных сообщений и сбоев. Сохранить запрет релиза с ошибками high/highest. |

Для инициативы 2 изменение заказа и событие для отправки сохраняются в одной транзакции БД. Отдельный отправитель передаёт событие в RabbitMQ и повторяет отправку при сбое. Получатель проверяет `message_id`, чтобы повторное сообщение не выполнило действие ещё раз.

RabbitMQ должен подтверждать публикацию сообщения. Получатель подтверждает обработку — `ack` — после успешного выполнения операции.

Для вызовов недоступных зависимостей используем тайм-ауты и Circuit Breaker: он временно прекращает повторные обращения к неисправному сервису. Пользователь получает понятный результат. Успешный приём задания подтверждаем только после его сохранения.

Backpressure ограничивает поступление новых расчётов. Размер очереди и количество одновременных расчётов должны быть ограничены.

## Целевая архитектура через полгода

Магазин, CRM и MES продолжают работать на текущих технологиях. Сохраняем RabbitMQ, S3 и общую Shop DB. Java-разработчики согласуют ответственность за общие данные и изменения их структуры.

MES API принимает задания, возвращает результаты и обслуживает операторов. Долгие расчёты выполняют фоновые обработчики. При перегрузке система отклоняет новый запрос либо сохраняет задание в ограниченную очередь.

Повторная доставка сообщения не создаёт новый заказ и не запускает производство повторно.

Списки заказов кешируются в Redis. Статус и назначение оператора хранятся в MES DB. При действии «Взять заказ» API проверяет актуальное состояние в БД.

Prometheus и Grafana показывают состояние приложений, БД, очередей и заказов. Логи доступны в ELK, цепочки вызовов — в Jaeger. По `order_id` можно найти события заказа, по `trace_id` — связанные вызовы.

Для критичных компонентов проверены резервирование и восстановление. Основные сценарии проходят автоматические проверки и ручную проверку на release. Выпуск в production остаётся управляемым.

## Если можно выполнить только три инициативы

Выбираю первые три:

1. Найти места задержек и ошибок.
2. Обеспечить надёжную передачу и обработку заказов.
3. Отделить расчёты от работы операторов и ускорить список.

План на шесть месяцев:

| Срок | Работа |
| --- | --- |
| Первый месяц | DevOps подключает метрики. Разработчики добавляют логи и трейсы обмена MES → RabbitMQ → CRM и обратных статусов. Продакт собирает примеры задержанных заказов. QA воспроизводит проблемы на release. |
| Второй и третий месяцы | Разработчики исправляют подтверждённые проблемы доставки и обработки. QA проверяет повторы сообщений, остановку получателя и восстановление после сбоя RabbitMQ. |
| Четвёртый–шестой месяцы | C#-разработчик и тимлид отделяют расчёт и ограничивают параллельную обработку. Добавляют кеш списка. Фронтенд-разработчик показывает состояние расчёта и обновляет список после действий. DevOps и QA сравнивают показатели при одинаковой нагрузке. |

Резервирование и полная автоматизация релизов остаются следующими инициативами. Дополнительный наём на старте не планирую. После первого месяца нужно оценить загрузку C#-разработчика и тимлида.
